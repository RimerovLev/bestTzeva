# Волна 1. Безопасность и аутентификация

## R-01 [КРИТИЧНО] Refresh-токен принимается как access-токен

**Файл:** `iam/service/JwtService.java` — `parseAccess()`, `generateAccess()`

**Проблема.** `generateRefresh` ставит claim `type=refresh`, а `generateAccess` не ставит никакого типа.
`parseAccess` проверяет подпись, издателя и срок, но не проверяет `type`. Оба токена подписаны одним
ключом и имеют одного издателя.

Следствие: refresh-токен, отправленный в заголовке `Authorization: Bearer`, успешно разбирается как
access. `JwtAuthenticationFilter` кладёт в контекст `AuthPrincipal` с `role = null` и выдаёт authority
`ROLE_null`, то есть запрос считается аутентифицированным. Любой эндпоинт с правилом `.authenticated()`,
включая `/api/v1/auth/me` и `/api/v1/me/**`, отработает по 30-дневному токену.

Это обесценивает всю схему: смысл 15-минутного access в том, что украденный долгоживущий refresh можно
отозвать в Redis, но фильтр в Redis не ходит, поэтому отозванный refresh продолжит работать как bearer
до истечения своих 30 дней.

**Что сделать.**
1. Добавить claim `type=access` в `generateAccess`.
2. В `parseAccess` требовать `type=access`, как это уже сделано для refresh в `parseRefresh`.
3. Отклонять токен с пустым или отсутствующим claim `role`, чтобы `ROLE_null` не мог появиться.

**Готово когда.** Тест: refresh-токен, переданный в заголовке `Authorization: Bearer`, даёт 401 на
`/api/v1/auth/me`. Тест: access-токен без claim `role` отклоняется. Существующие тесты IAM зелёные.

## R-02 [ВЫСОКАЯ] logout доверяет userId из переданного токена

**Файл:** `iam/service/AuthService.java` — `logout()`

**Проблема.** Метод получает `userId` аутентифицированного пользователя, но отзывает сессию по
`claims.userId()` из тела запроса: `refreshStore.revoke(claims.userId(), claims.tokenId())`.
Идентификатор из запроса нигде не сверяется с идентификатором из контекста. Аутентифицированный
пользователь A, предъявив refresh-токен пользователя B, погасит сессию B.

**Что сделать.** Сверять `claims.userId() == userId`; при расхождении не отзывать ничего и вернуть 401
(либо молча выйти — выбрать одно и задокументировать).

**Готово когда.** Тест: пользователь A отправляет в logout refresh-токен пользователя B; сессия B
остаётся активной, B может обновить токен.

## R-03 [ВЫСОКАЯ] logout без токена гасит все сессии пользователя

**Файл:** `iam/service/AuthService.java` — `logout()`

**Проблема.** При пустом `refreshToken` вызывается `revokeAllForUser`. Выход в одном браузере
выкидывает пользователя из приложения на телефоне и со всех остальных устройств. Это противоположно
ожидаемому поведению: массовый отзыв должен быть явным действием, а не поведением по умолчанию при
отсутствии необязательного поля.

**Что сделать.**
1. Сделать refresh-токен обязательным для `POST /api/v1/auth/logout`, отзывать только его.
2. Массовый отзыв вынести в отдельный `POST /api/v1/auth/logout-all`.
3. Сброс пароля продолжает отзывать все сессии — это правильно, не менять.

**Готово когда.** Тест: два входа одного пользователя, logout по одному токену; вторая сессия жива.
Тест: `logout-all` гасит обе. Тест: сброс пароля гасит обе.

## R-04 [ВЫСОКАЯ] Перечисление аккаунтов через различие 429 и 401

> Этот пункт вобрал в себя R-27. В первой редакции документа R-04 предлагал перенести защиту по
> логину в аспект, а R-27 — из аспекта в `AccountLockService`, то есть они противоречили друг другу.
> Ниже одно решение вместо двух. R-27 отозван и не выполняется.

**Файлы:** `iam/service/AuthService.java` — `login()`; `iam/service/AccountLockService.java`;
`iam/web/AuthController.java` — аннотации `@RateLimit` на `login`;
`common/web/ratelimit/RateLimitAspect.java`

**Проблема.** Константное время при отсутствии пользователя сделано правильно, через сравнение с
заглушечным хешем. Но проверка блокировки стоит **до** сравнения пароля и по `userId`, то есть
срабатывает только для существующих аккаунтов.

Атакующий отправляет 10 неверных паролей на подозреваемый адрес. Если адрес зарегистрирован,
одиннадцатая попытка вернёт `429 account_locked`; если нет — `401 invalid_credentials`. Разница в
ответах превращает защиту от перебора в оракул существования аккаунта.

Сейчас защита по логину живёт в двух местах сразу и обе работают по-разному:
`@RateLimit(key = "field:login", limit = 5, windowSeconds = 900)` в аспекте считает **все** попытки
по строке логина, а `AccountLockService` считает **только неудачи** по `userId`. Первая ничего не
знает о существовании аккаунта, вторая знает — отсюда и утечка.

**Решение (разделение ответственности).**

1. **Ответ клиенту определяет только лимитер.** Он ключуется по строке логина, которую прислал
   клиент, поэтому ведёт себя одинаково для существующих и несуществующих аккаунтов и может
   безопасно отдавать 429 с `Retry-After`. Оракула не возникает: атакующий, долбящий несуществующий
   адрес, получит ровно тот же 429.
2. **`AccountLockService` больше не влияет на HTTP-ответ.** Проверка `isLocked` из `login` убирается,
   заблокированный аккаунт получает тот же `401 common.auth.invalid_credentials`, что и неверный
   пароль. Сервис сохраняет состояние по `userId` только ради уведомления владельца (и это
   единственное, для чего ему нужен `userId`).
3. **Лимит по логину считает только неудачи.** Аспект проверяет бюджет до вызова, а факт неудачи
   регистрирует сам `AuthService` на ветке 401. Для этого в `RateLimiter` добавляется метод
   `record(key, window)` рядом с `tryAcquire`, а `@RateLimit` получает флаг вида
   `countOn = FAILURE` (при нём аспект только проверяет и не пишет). Это заодно закрывает исходную
   претензию R-27: пять успешных входов с разных устройств больше не исчерпывают лимит.
4. **Лимит по IP на `login` остаётся как есть** и продолжает считать все попытки — это нормальная
   практика и никакого оракула не создаёт.

Сознательный компромисс: ключ по строке логина позволяет намеренно тормозить вход конкретному
пользователю, зная его email. Поэтому по логину именно throttle со скользящим окном, которое само
рассасывается за 15 минут, а не жёсткая блокировка. Записать это в javadoc, чтобы следующий читатель
не «починил» его обратно в постоянный lock.

**Что сделать.**

1. Убрать `accountLock.isLocked(...)` и бросок `TooManyRequestsException` из `AuthService.login`.
2. `AccountLockService` оставить счётчик неудач по `userId` и уведомление владельцу; убрать
   `lockTtlSeconds` из публичного контракта, если он больше нигде не нужен.
3. Добавить `RateLimiter.record(...)` и флаг `countOn` в `@RateLimit`; на `login` пометить
   `field:login` как считающий только неудачи.
4. `AuthService.login` на ветке неверных учётных данных вызывает `record` по тому же ключу.

**Готово когда.**

- Тест: после исчерпания лимита ответы для существующего и несуществующего логина совпадают по
  статусу, коду, телу и заголовку `Retry-After`.
- Тест: пять успешных входов подряд с одного логина не приводят к 429.
- Тест: пять неудачных входов подряд приводят к 429 одинаково для обоих случаев.
- Тест: уведомление владельцу о подозрительной активности по-прежнему отправляется.

## R-05 [СРЕДНЯЯ] Нет реакции на повторное использование refresh-токена

**Файл:** `iam/service/AuthService.java` — `refresh()`

**Проблема.** `validateAndRotate` корректно возвращает false на уже отозванный токен, и пользователь
получает 401. Но предъявление отработавшего refresh-токена — классический признак кражи: легитимный

**Готово когда.** Тест: успешная ротация, затем повтор со старым токеном; все сессии пользователя
отозваны, уведомление зафиксировано.

## R-06 [СРЕДНЯЯ] Параллельное обновление токена разлогинивает пользователя

**Файл:** `iam/service/RefreshTokenStore.java` — `validateAndRotate()`

**Проблема.** Ротация атомарна, и это правильно, но у неё есть известное следствие. SPA при
перезагрузке часто отправляет два запроса на `/auth/refresh` почти одновременно (две вкладки либо
параллельные запросы, наткнувшиеся на 401). Один выигрывает, второй получает 401 и вышибает
пользователя из аккаунта. Это самый частый баг ротации refresh-токенов на практике.

**Что сделать.** Ввести короткое окно снисхождения: при успешной ротации сохранять в Redis запись
`auth:rotated:{tokenId}` с идентификатором пришедшей на смену пары и TTL 30 секунд. Повторный запрос
с тем же токеном внутри окна возвращает ту же новую пару вместо 401. За пределами окна — отказ и
поведение из R-05.

Взаимодействие с R-05 описать явно в javadoc: внутри окна повтор считается гонкой клиента, за
пределами окна — кражей.

**Готово когда.** Тест: два параллельных вызова refresh с одним токеном возвращают одну и ту же пару,
обе успешны. Тест: тот же токен через 31 секунду даёт 401 и отзыв сессий.

# Волна 2. Устойчивость и Redis

## R-09 [ВЫСОКАЯ] KEYS по всему пространству ключей на каждом входе

**Файл:** `iam/service/RefreshTokenStore.java` — `enforceSessionLimit()`, `revokeAllForUser()`

**Проблема.** Оба метода используют `redis.keys("auth:refresh:{userId}:*")`. Команда `KEYS` обходит
всё пространство ключей Redis и блокирует сервер на время обхода. `enforceSessionLimit` вызывается
при каждом успешном входе и каждом обновлении токена.

В этом же Redis по плану будут жить корзины (T-6.1), ключи rate limit, OTP и кэш каталога — десятки и
сотни тысяч ключей. Каждый вход будет обходить их все. На пустой базе не воспроизводится вообще.

**Что сделать.** Держать индекс сессий пользователя явно: sorted set `auth:refresh:{userId}`, где
member — tokenId, score — createdAt.

- лимит сессий: `ZCARD` + `ZRANGE` по старейшим;
- массовый отзыв: чтение членов + `DEL` по списку + `DEL` самого индекса;
- при отзыве одной сессии — `ZREM` вместе с удалением hash.

Обход пространства ключей исчезает совсем. Это же изменение закрывает R-11.

**Готово когда.** В коде нет вызовов `redis.keys`. Тест: 6-й вход при `max-sessions=5` вытесняет
самую старую сессию. Тест: `revokeAllForUser` гасит все сессии и не оставляет мусора в индексе.

## R-10 [СРЕДНЯЯ] Запись сессии и установка TTL не атомарны

**Файлы:** `iam/service/RefreshTokenStore.java` — `issue()`;
`iam/service/AccountLockService.java` — `recordFailure()`

**Проблема.** В `issue`: `opsForHash().putAll(key, ...)` и `redis.expire(key, ttl)` — две отдельные
команды. Обрыв соединения между ними оставляет hash refresh-сессии без TTL, то есть навсегда.

Тот же дефект в `recordFailure`: `INCR`, и только при значении 1 выставляется `EXPIRE`. Если `EXPIRE`
не выполнился, счётчик неудачных входов становится вечным, и аккаунт блокируется на десятой неудаче
за всё время жизни, а не за 15 минут.

**Что сделать.** Обе пары свести в один Lua-скрипт либо использовать формы со встроенным сроком:
`HSET` + `PEXPIRE` в одном `eval`; для счётчика — `SET key 0 EX 900 NX` с последующим `INCR`.

**Готово когда.** Тест: после `issue` у ключа сессии всегда положительный TTL. Тест: счётчик неудач
истекает через окно даже при единственной неудачной попытке.

# Волна 3. Схема и целостность данных

## R-14 [СРЕДНЯЯ] Перенос поддерева обходит ограничение глубины категорий

**Файл:** `db/migration/V3__catalog.sql` — `enforce_category_max_depth()`

**Проблема.** Триггер поднимается вверх по дереву от изменяемой строки и запрещает глубину больше
трёх, но проверяет только саму строку, а не её потомков.

Пусть категория C на первом уровне имеет потомков D (второй уровень) и E (третий). Переносим C под
категорию второго уровня: C становится третьим уровнем, триггер видит глубину 3 и пропускает. D
оказывается на четвёртом, E на пятом, и никакой триггер по ним не срабатывает.

**Что сделать.** Проверять также высоту поддерева: рекурсивным CTE посчитать высоту поддерева
переносимой категории и сложить с новой глубиной. Либо перенести проверку в сервис категорий на
T-4.1, оставив триггер только против прямых вставок в БД.

**Готово когда.** Тест: перенос категории с двумя уровнями потомков под категорию второго уровня
отклоняется.

## R-15 [СРЕДНЯЯ] Нарушение глубины категорий вернётся клиенту как 500

**Файл:** `db/migration/V3__catalog.sql` — `enforce_category_max_depth()`

**Проблема.** `raise exception` без указания кода даёт SQLSTATE `P0001`. Spring отображает его в
`UncategorizedSQLException`, а не в `DataIntegrityViolationException`, поэтому обработчик конфликтов
его не поймает, и запрос уйдёт в последний рубеж как 500 с записью ERROR в лог.

**Что сделать.** Поднимать исключение с явным SQLSTATE из класса нарушений целостности:
`raise exception '...' using errcode = '23514';`. Либо, вместе с R-14, перенести правило в сервисный
слой и отдавать `ConflictException`.

**Готово когда.** Тест: попытка создать категорию четвёртого уровня даёт 409 в формате problem+json,
а не 500.
