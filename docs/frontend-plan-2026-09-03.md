# План разработки фронтенда

**Бэкенд на коммите `126d299`.** План привязан к фактически существующим эндпоинтам, а не к
постановке: контроллеры перечитаны, расхождения с планом бэкенда вынесены в раздел «Предпосылки».

## Принятые решения

| Решение | Выбор | Следствие |
|---|---|---|
| Структура | Два приложения: `web` на Next.js (витрина) и `admin` на Vite + React (админка) | Витрине нужен SSR ради индексации красок и услуг; админке SEO не нужен, а нужна быстрая сборка. Общий UI-kit выносится в пакет только если начнёт дублироваться, не заранее |
| Языки | Иврит (основной, RTL) и русский | Английский добавляется позже без переделок: i18n закладывается на три локали, наполняются две |
| Токены | Refresh в httpOnly-куке, access в памяти вкладки | Требует правок бэкенда (см. B-01). Любой XSS в админке иначе отдаёт злоумышленнику 30-дневную сессию сотрудника |

# Предпосылки: правки бэкенда

Четыре вещи фронт не может обойти. Делать до начала F1, иначе придётся переписывать.

## B-01 [M] Refresh-токен в httpOnly-куке

```
Переведи выдачу refresh-токена в Tzeva Best с тела ответа на httpOnly-куку.

Сейчас POST /api/v1/auth/login и /refresh возвращают refresh_token в JSON, а фронт обязан его где-то
хранить. Любой XSS в админке при этом отдаёт 30-дневную сессию сотрудника.

Реализовать:
1. Login, register и refresh ставят refresh в куку: httpOnly, Secure (кроме local), SameSite=Lax,
   Path=/api/v1/auth, Max-Age равен сроку жизни refresh. В теле ответа остаются только access_token и
   expires_in.
2. POST /auth/refresh и /auth/logout читают токен из куки. Поле в теле оставить как запасной путь за
   флагом конфигурации: мобильное приложение, если появится, кукой пользоваться не сможет.
3. Logout и logout-all гасят куку (Max-Age=0).
4. Вернуть CORS allowCredentials=true (он был выключен по R-32 именно потому, что кук не было) и
   сузить allowed-origins до конкретных доменов витрины и админки: со звёздочкой браузер куку не
   отправит.
5. SameSite=Lax защищает от CSRF только при разных доменах фронта и API. Если админка и API будут на
   одном домене, добавить на /auth/refresh проверку заголовка Origin против allow-list, а не
   полагаться на SameSite.
6. Обновить docs/account-lifecycle.md и описание OpenAPI.

Готово когда: тесты покрывают вход с установкой куки, обновление токена по куке без тела, выход с
гашением куки и отказ при чужом Origin.
```

## B-02 [S] Slug для товара

```
Добавь slug товарам Tzeva Best. Сейчас в products его нет, а публичная карточка отдаётся по
GET /api/v1/products/{id}.

Для витрины это блокер: адрес вида /products/8412 не индексируется по названию краски, а именно
поисковый трафик по названиям и брендам — основной смысл SSR.

Реализовать:
1. Миграция: колонка slug varchar(160) not null unique. Генерация из английского названия по тем же
   правилам, что уже работают для категорий (CategoryService), с числовым суффиксом при коллизии.
   Backfill для существующих строк в той же миграции.
2. GET /api/v1/products/{slug} рядом с существующим по id. По id оставить для админки.
3. Slug редактируется вручную в админском CRUD; при смене отдавать 301 со старого на новый, для чего
   завести product_slug_history (slug, product_id, created_at).
4. Тот же приём проверить для портфолио: там slug уже есть, история редиректов — нет.

Готово когда: карточка открывается по slug, старый slug после переименования отдаёт 301.
```

эндпоинтов без реализации.

Готово когда: в admin-группе OpenAPI не осталось маршрутов, не соответствующих текущему объёму.
```

## B-04 [S] Расчёт расхода краски

```

# Приложение 1: витрина (Next.js)

## F1. Каркас витрины

### F-1.1 [M] Инициализация проекта и дизайн-токены

```
Создай приложение витрины Tzeva Best: Next.js 15 (App Router), TypeScript strict, pnpm.

Реализовать:
1. Структура: app/[locale]/... , локали he и ru, дефолт he. Локаль в пути, а не в куке: нужны
   отдельные индексируемые адреса на каждый язык.
2. RTL: атрибуты dir и lang на html из локали. Стили только на логических свойствах CSS
   (margin-inline-start вместо margin-left, inset-inline и так далее) — так одна таблица стилей
   работает в обе стороны без зеркалящих переопределений.
3. Дизайн-токены из макетов клиента: тёплый нейтральный фон, тёмно-синий, терракотовый и оливковый
   акценты, золотая линия в шапке. Задать CSS-переменными в одном файле, никаких цветов по месту.
4. Шрифты: ивритский с поддержкой никуда (Heebo или Assistant) и латиница/кириллица (Inter или
   аналог), подключение через next/font с subset и display=swap.
5. Tailwind с настроенными логическими утилитами, либо CSS Modules — выбрать одно и записать в
   README почему.
6. Базовый layout: шапка с переключателем языка и телефоном магазина, подвал с реквизитами.

Ограничения: не тащить UI-библиотеку целиком ради пяти компонентов. Кнопка, поле, селект, модалка и
скелетон пишутся свои поверх токенов.

Готово когда: страница-заглушка открывается на обеих локалях, переключение меняет направление текста
и адрес, Lighthouse не жалуется на шрифты и CLS.
```

### F-1.2 [M] Типизированный клиент API

```
Свяжи витрину Tzeva Best с бэкендом через типы, сгенерированные из OpenAPI, а не написанные руками.

Реализовать:
1. Скрипт генерации типов из /api-docs/public (openapi-typescript или orval). Результат коммитится,
   генерация гоняется в CI и падает, если сгенерированное разошлось с закоммиченным.
2. Тонкая обёртка fetch: базовый URL из окружения, заголовок Accept-Language из текущей локали,
   X-Request-Id (генерируется на клиенте, бэкенд его подхватывает), таймаут, разбор ответа.
3. Обработка ошибок в формате RFC 9457, который бэкенд отдаёт везде: тип ProblemDetail с полями code,
   detail, errors, trace_id. Из code берётся человеческий текст из словаря локали; detail с сервера
   показывается только если своего текста нет.
4. trace_id из ответа выводится в консоль и в сообщение об ошибке мелким шрифтом: по нему поддержка
   находит запрос в логах.
5. Серверные и клиентские вызовы через один модуль: на сервере через fetch с revalidate, на клиенте
   через TanStack Query.

Готово когда: изменение схемы на бэкенде ломает сборку фронта, а не проявляется в рантайме.
```

```

   скрипты, кроме аналитики.

   запросом на сервере. Это главная причина прокидывать X-Request-Id из F-1.2.
6. Бюджет бандла в CI: превышение ломает сборку.

Готово когда: обе выкладки автоматические, CSP не ломает страницы, ошибка на фронте находится в логах
бэкенда по trace_id.
```

# Порядок и оценка

| Волна | Состав | Оценка |
|---|---|---|
| 0 | B-01 … B-04 (правки бэкенда) | ~1 неделя |
| 1 | F-1.1, F-1.2, F-6.1 (каркасы обоих приложений) | ~2 недели |
| 2 | F-2.1, F-2.2, F-2.3, F-3.1 (каталог и заявка — ядро витрины) | ~3 недели |
| 3 | F-7.1, F-7.2, F-8.1 (каталог и склад в админке) | ~3 недели |
| 4 | F-4.1, F-4.2, F-4.3, F-9.1, F-9.2 (услуги на обеих сторонах) | ~3 недели |
| 5 | F-5.1, F-5.2, F-10.1, F-10.2 (контент, SEO, дашборд, отчёты) | ~2 недели |
| 6 | F-11.1, F-11.2 (качество и запуск) | ~2 недели |

Итого ориентировочно **15–16 недель** на одного фронтенд-разработчика, около 9–10 при двух с
разделением по приложениям: витрина и админка почти не пересекаются, общее у них только токены
дизайна и клиент API.

**Что можно выпустить раньше.** После волн 1–2 витрина уже собирает лиды по товарам: каталог,
карточка, заявка. Если заявки первое время обрабатывать вручную по письмам, публичную часть можно
запускать, не дожидаясь админки. Обратный порядок не работает: админка без витрины не приносит ничего.

**Риски, которые стоит держать в виду.**

RTL съедает больше времени, чем кажется по смете. Ломается не текст, а иконки со стрелками, отступы,
таблицы и графики. Отсюда скриншотные тесты на обеих локалях в F-11.1, а не в конце проекта.

Контент на двух языках — это работа клиента, и обычно она становится узким местом. Тексты услуг,
описания категорий и политика конфиденциальности нужны к волне 5, просить их стоит на волне 2.

Макеты есть на три экрана: витрина каталога, промо-страница и дашборд. Остальные двадцать с лишним
экранов рисуются по ходу от токенов и компонентов. Либо заложить время дизайнера, либо согласовать с
клиентом, что остальное собирается из той же системы без отдельного согласования каждого экрана.
