# Развёртывание (T-14.4)

## Образ

Многоступенчатый `Dockerfile` (бэкенд): сборка на `temurin:21-jdk`, рантайм на `temurin:21-jre-alpine`,
непривилегированный пользователь `app`, `MaxRAMPercentage=75`, `ENV SPRING_PROFILES_ACTIVE=prod`,
HEALTHCHECK по `/actuator/health/readiness`. Тесты (Testcontainers, нужен Docker) гоняет CI, не сборка.

**Фронтенд (аудит п.4):**
- `web/Dockerfile` — витрина Next в режиме `standalone`, рантайм `node:22-alpine`, non-root;
  `NEXT_PUBLIC_*` инлайнятся на сборке, поэтому адреса API/сайта передаются build-args в CI.
- `admin/Dockerfile` + `admin/nginx.conf` — статика Vite раздаётся nginx со строгими заголовками
  безопасности и CSP (аудит п.11); SPA-fallback на `index.html`.

## CI/CD (GitHub Actions)

- **PR** (`pr.yml`): `./gradlew check` (юнит + интеграционные на Testcontainers + порог JaCoCo) и
  скан зависимостей Trivy (HIGH/CRITICAL → красный).
- **merge в main** (`main.yml`): тесты → сборка образов бэкенда, витрины и админки, тег по git-хешу,
  публикация в GHCR, **блокирующий** скан каждого образа Trivy (HIGH/CRITICAL → красный) → деплой на
  staging → smoke по `/actuator/health/readiness`. Прод — отдельный job с ручным подтверждением
  (environment protection), предыдущий тег сохраняется для отката. Реальная выкатка (ECS/k8s) и цель
  деплоя задаются окружением — шаги `deploy-*` остаются шаблоном под конкретную инфраструктуру.

## Миграции (совместимость и без простоя)

Flyway применяется **отдельным шагом ДО старта нового контейнера**, а не приложением при старте:
иначе при нескольких инстансах возможна гонка. В prod задать `SPRING_FLYWAY_ENABLED=false` для
приложения; миграции гоняет CI-шаг (`flyway migrate` с prod URL/креды из секретов).

**Правило совместимости:** миграция обязана быть обратно совместима с ПРЕДЫДУЩЕЙ версией кода
(rolling deploy). Не удалять/переименовывать колонку в том же релизе, что перестаёт её писать —
двухфазно: (1) добавить новое + писать в оба, (2) следующий релиз перестаёт читать старое, (3) ещё
позже — удалить. Все существующие миграции только добавляют (V1…V49).

## Секреты

Только из окружения CI и AWS Secrets Manager / SSM Parameter Store — не в репозитории. В prod
обязательны (без дефолтов): `JWT_SECRET`, `NOTIFICATION_WEBHOOK_SECRET`,
`NOTIFICATION_UNSUBSCRIBE_SECRET`, `SPAM_SIGNING_SECRET`, `PRIVACY_PSEUDONYM_SECRET`, а также реквизиты
SMTP/SMS/S3 и `CORS_ALLOWED_ORIGINS`/`TRUSTED_PROXIES`. В `application.yml` dev-дефолты помечены
`dev-only`. Подстраховка: `ProdSecretsGuard` (профиль `prod`) не даёт приложению стартовать, если
какой-либо секрет оставлен dev-дефолтом, пустым или слишком коротким.

## Откат

Предыдущий тег образа сохранён. Откат = задеплоить предыдущий тег. Если проблема в миграции —
см. `docs/disaster-recovery.md` (миграции обратно совместимы, поэтому старый код работает с новой
схемой; при необходимости — восстановление из снапшота).

## Проверено

PR-проверки автоматические; merge в main доводит образ до staging. Реальный прогон CI, публикация и
деплой выполняются в GitHub/облаке — вне среды разработки (эти файлы — конвейер).
