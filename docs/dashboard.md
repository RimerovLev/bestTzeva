# Дашборд админки (T-13.1)

Эндпоинты `GET /api/v1/admin/dashboard/*` (доступ SUPPORT/MANAGER/ADMIN). Все агрегаты считаются
на стороне БД одним SQL на показатель.

## Эндпоинты

- `summary?from=&to=` — заявки на товар и на покраску за сегодня; за период с изменением к
  предыдущему периоду той же длины (%); позиции ниже порога остатка; позиции в резерве; конверсия
  обеих воронок.
- `requests-chart?from=&to=&granularity=day|week|month` — временной ряд обоих типов; пропущенные
  бакеты заполняются нулями через `generate_series` (график не рвётся).
- `top-colors?limit=`, `top-products?limit=`, `top-categories?limit=` — доля по количеству
  запрошенных единиц за период.
- `recent-requests?limit=` — последние заявки обоих типов.

## Правило спроса и конверсии

Заявки в статусах **CANCELLED / LOST исключаются из показателей спроса** (топы цветов/товаров/
категорий — считают только фактический интерес), но **учитываются в конверсии**: конверсия =
`COMPLETED / всего заявок` (знаменатель включает отменённые и потерянные, иначе воронка приукрашена).

Изменение к периоду: `(current − prev) / prev · 100`. Рост с нуля процентом не выражается (`null`).

## Производительность и кэш

- Каждый показатель — один агрегирующий SQL; счётчики summary собираются условными агрегатами
  (`count(*) filter (...)`), а не пятью отдельными запросами на таблицу (по духу R-48).
- Результаты кэшируются на 5 минут (`ConcurrentMapCacheManager("dashboard")`), инвалидация — по
  расписанию (`app.dashboard.cache-evict`, дефолт PT5M), а не по каждой заявке.

## Тесты

`DashboardTest`: конверсия учитывает отменённые, топ цветов их исключает; топ товаров/категорий
агрегируют спрос; ряд заполняет пропуски нулями.
