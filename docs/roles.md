# Роли и права доступа — Tzeva Best

Роли хранятся в `users.role` (varchar + check). Аутентификация выдаёт access-токен с claim
`role`; авторизация — Spring Security (chain-правила для `/api/v1/admin/**` + `@PreAuthorize`
на админских сервисах) и проверка владения ресурсом (`@ownership`).

> **Заведение аккаунтов (T-16.2).** После сноса онлайн-покупки аккаунты нужны только персоналу.
> Публичная регистрация закрыта флагом `app.auth.public-registration-enabled` (по умолчанию `false`,
> `POST /auth/register` → `404`). Пользователей заводит администратор через смену роли
> (`AdminUserController`); роль `CUSTOMER` остаётся в модели, но не выдаётся. Первый администратор —
> `AdminBootstrap` на пустой базе из переменных окружения. Подробности — в `account-lifecycle.md`.

## Зоны ответственности

| Роль        | Ответственность |
|-------------|-----------------|
| `CUSTOMER`  | Покупатель. Видит только **свои** заказы, адреса и заявки. |
| `SUPPORT`   | Поддержка. Читает заказы и заявки, меняет статусы **заявок**. Не правит каталог и цены, не видит финансовые отчёты, не правит остатки. |
| `WAREHOUSE` | Склад. Читает заказы, правит **остатки**. Не видит финансовые отчёты, не правит каталог/цены/статусы заявок. |
| `MANAGER`   | Менеджер. Полный доступ к каталогу, заказам, заявкам, остаткам и **отчётам**. Не управляет пользователями и ролями. |
| `ADMIN`     | Администратор. Без ограничений, включая управление пользователями и ролями. |

Служебные роли (`SUPPORT`, `WAREHOUSE`, `MANAGER`, `ADMIN`) имеют доступ в админ-зону
`/api/v1/admin/**` (роль **не ниже SUPPORT**). `CUSTOMER` в админ-зону не допускается.

## Матрица прав (эндпоинт × роль)

`✓` = 200 (доступ разрешён), `✗` = 403 (запрещено). Все `/api/v1/admin/**` для `CUSTOMER` — `✗`
на уровне цепочки (не служебная роль).

| Эндпоинт | Зона | CUSTOMER | SUPPORT | WAREHOUSE | MANAGER | ADMIN |
|----------|------|:--------:|:-------:|:---------:|:-------:|:-----:|
| `GET /api/v1/admin/orders` | чтение заказов | ✗ | ✓ | ✓ | ✓ | ✓ |
| `PUT /api/v1/admin/inventory` | правка остатков | ✗ | ✗ | ✓ | ✓ | ✓ |
| `PUT /api/v1/admin/service-requests/{id}/status` | статусы заявок | ✗ | ✓ | ✗ | ✓ | ✓ |
| `PUT /api/v1/admin/catalog` | правка каталога/цен | ✗ | ✗ | ✗ | ✓ | ✓ |
| `GET /api/v1/admin/reports/finance` | финансовые отчёты | ✗ | ✗ | ✗ | ✓ | ✓ |
| `POST /api/v1/admin/users/{id}/role` | смена ролей | ✗ | ✗ | ✗ | ✗ | ✓ |

## Владение ресурсом

Для клиентских ресурсов (адреса, заказы, заявки) доступ проверяется по владельцу:
`@PreAuthorize("@ownership.owns('address', #id)")`. Правило:

- владелец (`resource.user_id == currentUser.id`) — разрешено;
- `ADMIN` и `MANAGER` — проверка пропускается (полный доступ);
- иначе — 403.

| Эндпоинт | Владелец (A) | Чужой (B) | MANAGER/ADMIN |
|----------|:------------:|:---------:|:-------------:|
| `GET /api/v1/me/addresses/{id}` | ✓ | ✗ | ✓ |

Провайдеры владения регистрируются модулями-владельцами ресурса (`address` — iam;
`order` — модуль заказов при появлении эндпоинтов) через `OwnershipProvider`.
