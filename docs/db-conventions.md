# Соглашения по схеме БД — Tzeva Best (PostgreSQL 16)

Схема меняется **только** через Flyway-миграции (`src/main/resources/db/migration`).
`spring.jpa.hibernate.ddl-auto=validate` — Hibernate ничего не создаёт и не меняет,
только сверяет маппинг со схемой.

## Именование

| Объект            | Правило                                              | Пример                          |
|-------------------|------------------------------------------------------|---------------------------------|
| Таблица           | множественное число, snake_case                      | `users`, `user_addresses`       |
| Первичный ключ    | всегда `id bigint generated always as identity`      | `id`                            |
| Внешний ключ      | явное имя `fk_<таблица>_<поле>`                       | `fk_user_addresses_user_id`     |
| Уникальность      | `uq_<таблица>_<поле(я)>`                              | `uq_users_phone`                |
| Check-ограничение | `ck_<таблица>_<поле>`                                 | `ck_users_role`                 |
| Индекс            | `ix_<таблица>_<поле(я)>` (обычный), `ux_…` (unique)  | `ix_user_addresses_user_id`     |
| Триггер           | `trg_<таблица>_<действие>`                            | `trg_users_set_updated_at`      |

## Типы

- **Время** — `timestamptz` (в БД UTC). На всех таблицах с бизнес-смыслом обязательны
  `created_at` и `updated_at` (оба `timestamptz not null default now()`).
- **Деньги** — `numeric(12,2)`, валюта хранится отдельным полем (ILS).
- **Enum** — хранится как `varchar` с `check`-ограничением, **не** как postgres enum type
  (проще эволюционировать без ALTER TYPE). В БД лежит имя Java-константы в верхнем регистре
  (Hibernate `@Enumerated(STRING)`); в JSON API значение отдаётся в нижнем регистре.
- **Строки** — `varchar(n)` с осмысленной длиной; `text` — для заведомо длинных полей.

## Время обновления

Общая триггерная функция `set_updated_at()` проставляет `updated_at = now()` в `BEFORE UPDATE`.
Триггер вешается на каждую таблицу с `updated_at` — так поле корректно и при обновлении
напрямую через SQL, а не только через приложение.

В сущностях (`BaseEntity`) `created_at`/`updated_at` проставляет **приложение** в
lifecycle-колбэках `@PrePersist`/`@PreUpdate`, а не `@Generated`. Причина: `@Generated`
заставляет Hibernate делать дополнительный `SELECT` для вычитывания значения на каждый
`INSERT`/`UPDATE`, что удваивает round-trip в пакетных операциях (напр. склад, T-5.1).
Триггер `set_updated_at` и `default now()` в БД остаются **страховкой** для изменений в обход
ORM. append-only таблицы (журналы/история) без `updated_at` используют `@Generated(INSERT)`
для `created_at` — там это единичная вставка без цикла обновлений.

## Идемпотентность и неизменяемость миграций

- Версия миграции задаётся именем файла `V<n>__<описание>.sql`; после мержа файл
  **не редактируется** — исправления идут новой миграцией.
- Расширения включаются через `create extension if not exists`.

## Первичные ключи и идентичность

- `id bigint generated always as identity` — приложение не подставляет `id` вручную
  (Hibernate `GenerationType.IDENTITY`).

## Append-only журналы (audit_log, consents) и TRUNCATE (R-38)

Таблицы `audit_log` и `consents` защищены от изменения построчными триггерами
`before update or delete`, поднимающими исключение. Два сознательных решения:

- **`TRUNCATE` намеренно оставлен как привилегия владельца схемы.** Построчные триггеры на
  `TRUNCATE` не срабатывают, поэтому append-only через `TRUNCATE` формально обходится. `before
  truncate`-триггер не добавляется намеренно: тестовый харнес (`resetState`) очищает таблицы через
  `TRUNCATE ... CASCADE`, и ломать его не нужно. В проде роль приложения не имеет прав
  `TRUNCATE/UPDATE/DELETE` на этих таблицах (выдаётся только владельцу-мигратору); защита от правки
  журнала опирается на модель прав, а построчные триггеры закрывают `UPDATE/DELETE` для всех ролей.
- **Код ошибки `0A000` (feature_not_supported) → HTTP 500 выбран сознательно.** Попытка изменить
  журнал аудита — ошибка программиста/оператора, а не клиента, поэтому 500 уместнее, чем 409. Это
  отличается от `V16` (глубина категорий), где нарушение приходит от клиента и поднимается с `23514`
  ради согласованного 409.

## Ужесточающие миграции обязаны нести backfill (R-39)

Миграция, ужесточающая ограничение (`set not null`, новый `check`, `unique`), обязана сначала
привести существующие данные в соответствие (`update ... where <нарушает>`), и лишь затем менять
ограничение. На пустой базе backfill — no-op, но на таблице с данными его отсутствие роняет
миграцию на проде. Пример: `V26` заполняет `consents.policy_version` для старых строк перед
`set not null`.
